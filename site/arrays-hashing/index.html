Массивы, списки и хеш-таблицы

Почему вставка в начало списка стоит O(n), откуда у словаря O(1) и когда оно превращается в O(n), как устроены dict в Python, map в Go и HashMap в Java — и как узнать задачу на хеш-таблицу на собеседовании.

Листайте стрелками ← →, свайпом или кнопками внизу. В схемах нажимайте кнопки, вводите ключи и двигайте ползунки.

Массив: быстро по индексу, дорого в середине

Массив — непрерывный кусок памяти: адрес i-го элемента = начало + i × размер элемента. Отсюда O(1) по индексу и быстрый последовательный проход. Но вставка или удаление в середине сдвигает весь хвост — O(n).

  • Динамический массив — list в Python, slice в Go, ArrayList в Java, Array в JS — держит запас ёмкости. Место кончилось — выделяет блок побольше и копирует всё.
  • Рост в k раз даёт амортизированное O(1) на append: копирований за всё время — не больше n·1/(k−1).
  • list в Python хранит указатели на объекты, а не числа подряд — об этом в «Данных в памяти».

Связный список: красиво на доске, медленно в жизни

Каждый узел — отдельный объект в куче. Адрес следующего узнаётся, только когда прочитан текущий, поэтому процессор не может подгрузить его заранее: каждое звено — возможный промах кэша, ~100 нс (подробнее о кэшах).

  • Список нужен, когда узел уже найден и его надо вынуть или переставить за O(1): LRU-списки (memcached, functools.lru_cache), списки свободных блоков в аллокаторах, list_head в ядре Linux — узел встроен прямо в структуру.
  • LinkedList в Java почти всегда медленнее ArrayList — даже на вставках в середину: найти позицию — те же O(n), но с промахами.
  • collections.deque — компромисс: двусвязный список блоков по 64 элемента.

Стек, очередь, дек и кольцевой буфер

  • Стек (последним пришёл — первым ушёл): append/pop у list, slice в Go, ArrayDeque в Java. Вызовы функций, отмена действий, скобки, обход в глубину.
  • Очередь и дек — кольцевой буфер: head и tail бегут по кругу, элементы не сдвигаются. Так устроены ArrayDeque, буфер канала в Go (про каналы), очереди сетевой карты, io_uring, буфер perf.
  • При переполнении кольцо либо растёт (копия с «распрямлением»), либо затирает самое старое — так живут логи и метрики фиксированного размера.

Нажимайте кнопки и следите, как индексы переходят через конец массива: (i + 1) % cap.

Проверьте себя

Воркер на Python разбирает очередь задач: tasks — обычный list на 1 000 000 элементов, в цикле task = tasks.pop(0), пока список не опустеет. Сколько это стоит?

pop(0) делает memmove всех оставшихся указателей на одну позицию: в сумме n²/2 ≈ 5·10¹¹ перемещений, терабайты копирования. Очередь в Python — collections.deque с popleft() за O(1). То же в Go: q = q[1:] дёшево, но держит в памяти весь старый массив; в JS Array.shift() на больших массивах тоже O(n).

Хеш-функция: от ключа к корзине

Хеш-функция превращает ключ в число, а остаток от деления на размер таблицы m — в номер корзины. Хорошая функция раскидывает даже похожие ключи равномерно: в каждой корзине ≈ n/m ключей.

  • m обычно степень двойки: вместо деления — h & (m − 1), то есть младшие биты. Java поэтому подмешивает к ним старшие: h ^ (h >>> 16).
  • Реальные функции: SipHash-1-3 для str в Python, aeshash/wyhash в Go, 31·h + c в Java String.hashCode(). Строки кэшируют свой хеш — второй раз он не считается.

Введите ключ и выберите функцию. Гистограмма — 1000 ключей user:1…user:1000.

Коллизии: цепочки или открытая адресация

Два ключа попали в одну корзину — это нормально, вопрос в том, где хранить второй.

Цепочки (separate chaining)

0"id"
1
2"ts"→"ip"→"ua"
3"user"
  • Корзина — список (или дерево) элементов. Удаление простое, перегрузку таблица переживает плавно.
  • Но узел — отдельная аллокация, а поиск — прыжки по памяти.
  • Java HashMap, C++ std::unordered_map, Go map до 1.24 (корзины по 8 + overflow-корзины).

Открытая адресация

"id""ts""ip""ua""user"
"ip" и "ua" хотели в 2 → заняли следующие свободные
  • Всё в одном массиве. Корзина занята — идём дальше по правилу: линейно, квадратично или псевдослучайно.
  • Дружит с кэшем и не аллоцирует, но требует запаса места и надгробий при удалении.
  • Python dict и set, Go map с 1.24 (Swiss tables), Rust HashMap, Abseil flat_hash_map.

Линейное пробирование и надгробия

Вставка начинается с ячейки h(k) и идёт вправо до первого свободного места. Поиск идёт тем же путём и останавливается на пустой ячейке: дальше ключа быть не может.

  • Поэтому просто очистить ячейку при удалении нельзя — оборвётся путь к ключам за ней. Ставят надгробие (tombstone): поиск через него проходит, вставка может его занять.
  • Надгробия копятся и удлиняют поиск. Их вычищает перестройка таблицы.

Здесь h(k) = k mod 10 — последняя цифра. Вставьте 12, 22, 32, удалите 22 и найдите 32. Потом включите удаление без надгробия и повторите.

Заполненность и перестройка

Коэффициент заполнения α = n/m. При линейном пробировании поиск отсутствующего ключа стоит в среднем ½·(1 + 1/(1−α)²) проб: при α = 0,5 — 2,5, при 0,9 — уже 50. Поэтому таблицу расширяют заранее.

  • Рост — новый массив вдвое больше и вставка всех ключей заново: позиция h & (m−1) зависит от m. Одна вставка стоит O(n), в среднем — O(1).
  • Пороги: Python dict — 2/3, Java HashMap — 0,75, Go Swiss tables — 7/8.
  • Пауза на рехеш заметна: Redis переносит корзины постепенно, Go 1.24 растит большие map частями по 1024 слота. Знаете размер — задайте сразу: make(map[K]V, n), HashMap.newHashMap(n).

O(1) — в среднем. Атака hash flooding

O(1) обещано для «случайных» ключей. Если подобрать ключи с одинаковым хешем, таблица вырождается в список: n вставок — n²/2 сравнений.

  • В 2011 году показали: POST-запрос с тысячами подобранных параметров занимает ядро на минуты в PHP, Java, Python, Ruby, ASP.NET. В Java "Aa" и "BB" имеют один хеш — из таких блоков собирается 2k коллизий.
  • Защиты: секретный случайный seed (Python 3.3+ — PYTHONHASHSEED, в Go — свой seed у каждой map), дерево вместо длинной цепочки (Java 8), лимит числа параметров запроса.

Выберите защиту и двигайте число ключей.

Python dict изнутри

С 3.6 словарь — два массива: маленький разреженный массив индексов и плотный массив записей (хеш, ключ, значение) в порядке вставки. Поэтому dict помнит порядок — с 3.7 это гарантия языка — и занимает меньше памяти.

  • Проба: i = (5·i + 1 + perturb) mod m, а perturb >>= 5 — так в выбор ячейки входят все биты хеша.
  • Удаление оставляет дыру в записях и надгробие в индексах. Когда занято 2/3 индексов, словарь перестраивается в размер ≥ 3 × живых ключей — и заодно сжимает записи.

Добавляйте и удаляйте ключи. Хеши здесь условные: в настоящем Python хеш строки меняется от запуска к запуску.

Как устроены map в Go, Java и JS

Go map до 1.23Массив из 2B корзин по 8 пар + 8 байт «tophash» (старшие биты хеша) для быстрого отсева. Переполнилась — цепляется overflow-корзина. Рост при 6,5 элемента на корзину, постепенный: старые корзины переносятся при следующих записях.
Go map 1.24+Swiss tables: группы по 8 слотов + 8 контрольных байт с 7 битами хеша; одна операция сравнивает все 8 байт сразу. Открытая адресация по группам, заполнение до 7/8. Большая map — набор таблиц до 1024 слотов, каждая растёт отдельно.
Java HashMapМассив корзин размера 2k и цепочки. Корзина из 8+ элементов при таблице ≥ 64 превращается в красно-чёрное дерево — O(log n) даже при атаке. Рост ×2 при 0,75: цепочка делится на «осталась» и «сдвинулась на oldCap» без пересчёта хеша.
JS Map / Set (V8)Детерминированная хеш-таблица: цепочки индексов + записи в порядке вставки — та же идея, что compact dict. Объект с тысячами динамических ключей уходит в медленный «словарный режим» — для словарей берите Map.

Общее у всех: порядок обхода — деталь реализации. Go специально начинает обход со случайной позиции, чтобы никто на порядок не полагался. Ни одна из этих map не потокобезопасна: sync.Map/мьютекс в Go, ConcurrentHashMap в Java.

Хешируемость и изменяемые ключи

Контракт: равные объекты обязаны иметь равные хеши, а хеш не должен меняться, пока объект лежит в таблице. Нарушили — элемент «потерян»: он в таблице, но найти его нельзя.

  • Python: list, dict, set не хешируемы; @dataclass(frozen=True) — хешируем. Определили __eq__ — __hash__ сбрасывается в None.
  • Java: переопределили equals без hashCode — HashSet хранит «дубликаты»; поменяли поле ключа — remove() молча не работает.
  • Go: ключ — только comparable-тип. NaN != NaN, поэтому m[math.NaN()] = 1 каждый раз добавляет новую запись.

Что напечатает Python?

1 == True == 1.0 и hash(1) == hash(True) == hash(1.0) == 1 — для таблицы это один ключ. Второе и третье присваивание находят существующую запись и меняют только значение, а ключом остаётся первый объект — 1. На практике это ловят, когда смешивают в ключах int и float из JSON или bool и числа.

Множества

  • set — хеш-таблица без значений: in, add, remove — O(1) в среднем. А x in list — O(n), и проверка в цикле незаметно делает из O(n) O(n²).
  • a & b стоит O(min(|a|, |b|)): перебирается меньшее множество, каждый элемент ищется в большем.
  • Go: map[T]struct{} — пустая структура не занимает памяти. Java: HashSet — обёртка над HashMap, LinkedHashSet помнит порядок.
  • Миллиарды элементов и можно ошибаться в одну сторону — фильтр Блума (вероятностные структуры).

LRU-кэш = хеш-таблица + двусвязный список

Надо за O(1) найти ключ, за O(1) поднять его в начало и при переполнении выкинуть самый давний. Таблица даёт поиск и указатель на узел, список — порядок: узел вынимается из середины за O(1), потому что искать его не нужно.

  • functools.lru_cache — dict + кольцевой двусвязный список на C; руками — OrderedDict.move_to_end. Java: LinkedHashMap(…, true) + removeEldestEntry. Go: container/list + map.
  • Redis экономит память и списка не держит: берёт 5 случайных ключей и вытесняет самый давний — приближённый LRU.

Задачи на хеш-таблицу: как узнать

  • «Найти пару / дополнение / встречалось ли раньше» → dict или set увиденного: Two Sum за O(n) вместо O(n²).
  • «Сгруппировать по признаку» → словарь списков с каноническим ключом: "".join(sorted(w)), кортеж частот.
  • «Частоты, топ-k, анаграмма ли» → Counter.
  • «Самая длинная подстрока / подмассив, где …» → окно [l, r] + счётчики или последние позиции в dict.
  • «Сумма подмассива = k», есть отрицательные → префиксные суммы + dict (следующий слайд).

Размен почти всегда один: O(n) памяти ради O(n) времени. Проговаривайте его вслух.

Сумма подмассива равна k

Сумма nums[i..j] = Pj+1 − Pi, где P — префиксные суммы. На каждом шаге спрашиваем: сколько раз раньше встречался префикс s − k? Счётчик префиксов в dict отвечает за O(1) — итого O(n).


def subarray_sum(nums, k):
    seen = Counter({0: 1})   # пустой префикс
    s = count = 0
    for x in nums:
        s += x
        count += seen[s - k]
        seen[s] += 1
    return count

Скользящее окно не годится: с отрицательными числами сумма окна не растёт монотонно. Префиксы — и в жизни: счётчик в Prometheus только растёт, а значение за интервал — разность двух точек.

Проверьте себя

В Go-сервисе кэш — обычная map[string]*User. HTTP-обработчики пишут в неё из разных горутин без мьютекса. Что будет под нагрузкой?

Map в Go не защищена, и рантайм на лету ловит одновременную запись по флагу «идёт запись» — это не паника, а фатальная ошибка. Ловит не всегда: иногда таблица просто портится. Лечится sync.Mutex/RWMutex или sync.Map, а находится заранее go test -race. В Java старый HashMap при одновременном росте мог зациклить цепочку — поток вечно крутился на 100% CPU.

Как это увидеть у себя

  • Рост списка: sys.getsizeof прыгает в момент перевыделения.
  • Рандомизация хеша: запустите hash("abc") дважды; алгоритм — в sys.hash_info.
  • list против set: python -m timeit. Go: go test -bench . -benchmem покажет аллокации на рост map без ёмкости.
  • Гонки на map: go test -race; в Java — ConcurrentHashMap по умолчанию для общего состояния.
  • Ёмкость заранее: make([]T, 0, n), make(map[K]V, n), new ArrayList<>(n), HashMap.newHashMap(n) (Java 19+).

Главное

  • Массив — O(1) по индексу и лучший друг кэша; вставка в середину и pop(0) — O(n). Динамический массив растёт в k раз, и append амортизированно O(1).
  • Связный список нужен, когда узел уже найден: LRU, free list, ядро. Для перебора и поиска он проигрывает массиву в разы.
  • Очередь и дек — кольцевой буфер, а не сдвиги массива.
  • Хеш-таблица — массив + хеш-функция + правило для коллизий. O(1) — в среднем и при запасе места; рост стоит O(n) разом.
  • Ключ должен быть неизменяемым, а равные ключи — иметь равные хеши. Хеш от чужих данных — с секретным seed.
  • На собеседовании «пара, группа, частота, окно, сумма подмассива» — почти всегда dict.

O(1) — это обещание в среднем, а не гарантия. Гарантию дают seed, запас места и неизменяемые ключи.
